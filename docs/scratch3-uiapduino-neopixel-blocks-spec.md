# NeoPixel ブロック 実装仕様

scratch3-uiapduino の NeoPixel (WS2812B) 対応の実装仕様。
**実装済みの内容を書いてある。WS2812B の 12 連リングで実機確認済み（2026-08-13）。**

打ち合わせで決めた設計をそのまま実装したので、初版から変わった点は無い。
書き起こしのときに決めた細部は末尾の「修正履歴」にまとめてある。

**色の並び（カラーオーダー）を選ぶブロックを後から足した（[Issue #3](https://github.com/tarosay/scratch3-uiapduino/issues/3)）。**
足したのは Scratch 側だけで、デバイス側は変えていない。**焼き直しは要らない。**

---

## 0. 前提

| | 状態 |
|---|---|
| 現在のプロトコル | **バージョン 7**（v0.2.2 として公開済み） |
| このブロックを入れた後 | **バージョン 8** |
| デバイス側ライブラリ | `NeoPixelmin.h`（`arduino_core_ch32` v1.2.12 に同梱） |
| DIN のピン | **D8 (PC6) 固定**。ライブラリが SPI1 MOSI を使うため変えられない |
| LED の最大数 | **64**（`NEOPIXELMIN_MAX_LEDS`）。RAM 192 バイト |

### ⚠ 基板の書き込み直しが必要

`PROTOCOL_VERSION` を **7 → 8** に上げる。7 は v0.2.2 として配ってあるので据え置けない。
古いスケッチのままだと接続時のバージョン照合で弾かれる。

### `sketch.yaml` の固定は 1.2.12（上げ済み）

1.2.10 に `NeoPixelmin` は無い（初出は 1.2.11、`SysTick` 版は 1.2.12）ので、
**上げないとビルドが通らない。** README の記述も 1.2.12 に合わせてある。

### ⚠ SPI1 を使うものと同居できない

`NeoPixelmin` は SPI1 を占有する。`SPI.h` / `SDmin` とは同時に使えない。
このスケッチはどちらも使っていないので問題にならないが、将来 SD を足すときは衝突する。

消費されるのは MOSI (PC6 = D8) だけで、SCK (PC5 = D7) / MISO (PC7 = D9) /
NSS (PC1 = D3) はライブラリが触らない。**弾くのは D8 の 1 本だけでよい。**

## 1. 設計方針：色は Scratch 側のバッファに書く。USB へ出すのは「表示する」だけ

**Scratch 側に鏡のバッファ（JS の配列）を持つ。**
色を決めるブロックはこのバッファを書き換えるだけで、USB を触らない。
実際に送るのは「表示する」のときだけ。

理由は速さ。1 コマンドの往復に **12〜15ms** かかるので、LED を 1 個ずつ送ると
12 連のリングで 180ms かかり、アニメーションにならない。

この前提から次が決まる。

- **虹・回転・減衰・HSV の計算はすべて JS 側で行う。** デバイスは色を作らない
- **デバイス側のコマンドは 5 つで足りる。** 「虹を出す」に対応するコマンドは要らない
- **表現を増やしてもデバイスは変わらない。** 焼き直さずにブロックを足せる

### LED の個数は「始める」で渡す。デバイスは覚えるだけ

個数を持つのは Scratch 側。デバイスは `NEO_BEGIN` で言われた数を覚え、
`show()` でその数ぶんだけ波形を出す。こうすると
「LED を 24 個に増やしたい」で基板を焼き直さずに済む。

バッファ（`NEOPIXELMIN_MAX_LEDS` = 64）は入れ物の大きさであって、送る数ではない。

#### ⚠ 当初は「常に 64 個分を送る」形だった。実機で作り直した

物理的に 12 個しか繋がっていなければ、残り 52 個分のビットはチェーンの末端から
出ていって消える。WS2812 は自分の 24 ビットだけを取って残りを次へ流す素子なので、
**光り方だけを見れば多く送っても害が無い。** だから当初は個数を渡していなかった。

やめたのは、下記の `NEOPIXELMIN_ATOMIC` が要ることが実機で分かったため。
**割り込みを止めている時間が個数に比例する。** 12 個なら 0.38ms だが、
64 個だと 2.05ms 止まり、その間 USB がホストの問い合わせに応えられない。

### 自動表示は既定 ON

色を決めるブロックは、既定では**自分で「表示する」まで行う。**
置いただけで光らないと、利用者はどこが悪いのか分からない。

速さが要るところだけ「まとめて表示する〔 〕」の C ブロックで囲む。
囲みの中では自動表示が止まり、囲みを抜けるときに 1 回だけ送る。

## 2. ブロック

パレットの並び順に書く。番号は **1 から数える**（Scratch のリストと同じ）。

| ブロック（日本語） | 形 | 送るコマンド |
|---|---|---|
| `NeoPixel は 赤が [赤] 緑が [緑] に見える` | COMMAND | 送らない。次の送信の並べ替えが変わるだけ |
| `NeoPixel を [12] 個 明るさ [50] % で始める` | COMMAND | `BEGIN` + `BRIGHTNESS` + `FILL(0)` + `SHOW` |
| `NeoPixel の明るさを [50] % にする` | COMMAND | `BRIGHTNESS` |
| `NeoPixel の [1] 番を [■] にする` | COMMAND | 鏡のみ（+ 自動表示） |
| `NeoPixel の [1] 番を 赤 [255] 緑 [0] 青 [0] にする` | COMMAND | 鏡のみ（+ 自動表示） |
| `NeoPixel の [1] 番を 色 [0] 鮮やかさ [100] 明るさ [100] にする` | COMMAND | 鏡のみ（+ 自動表示） |
| `NeoPixel の [1] 番から [3] 個を [■] にする` | COMMAND | 鏡のみ（+ 自動表示） |
| `NeoPixel を全部 [■] にする` | COMMAND | 鏡のみ（+ 自動表示） |
| `NeoPixel を消す` | COMMAND | 鏡のみ（+ 自動表示） |
| `NeoPixel を [1] つ ずらす` | COMMAND | 鏡のみ（+ 自動表示） |
| `NeoPixel を [20] % 暗くする` | COMMAND | 鏡のみ（+ 自動表示） |
| `NeoPixel に虹を出す ずらし [0]` | COMMAND | 鏡のみ（+ 自動表示） |
| `NeoPixel を表示する` | COMMAND | `SET` × n + `SHOW` |
| `NeoPixel をまとめて表示する〔 〕` | **LOOP（囲み）** | 抜けるときに `SET` × n + `SHOW` |
| `NeoPixel の [1] 番の色` | REPORTER | 鏡から読む。USB を触らない |

**15 個。** 打ち合わせのメモには「12 個」と書いてあったが、
列挙されていた項目を数えると 14 になる。列挙の方を採った。
`赤が [ ] 緑が [ ] に見える` は Issue #3 で後から足したぶん。

### 色の並び（カラーオーダー）

テープ／リングは製品によって 1 画素 3 バイトの並びが違う。合わないものを使うと
色が入れかわる。今は線へ `[G, R, B]` の順で出しているので、GRB 以外の製品ではずれる。

**⚠ 商品説明の「RGB」はバイトの並びではない。** 「フルカラー」の意味で書かれて
いることが多い。手元の 12 連リングも説明は RGB だったが、実機で確かめると GRB
だった（2026-08-31）。**説明文ではなく、光らせて判定すること。**

#### ⚠ 並びを選ばせてはいけない。見えた色を答えさせる

**この節は 2 回作り直した結果。同じ失敗を繰り返さないこと。**

**1 案目：略語を並べたメニュー（GRB / GBR / …）。** これは駄目。
`NEO_GRB` などは `NeoPixelmin.h`（`Adafruit_NeoPixel` から写したもの）の**定数名**で、
**商品にも箱にも通販ページにも書いていない。** ファームウェアを書く人の共通語であって、
子どもには手がかりが 1 つも無い。

**2 案目：症状を文で書いたメニュー**（`赤と青が入れかわる`、`赤→緑→青にずれる`）。
これも駄目。**「赤→緑→青にずれる」は「1 番が赤、2 番が緑、3 番が青に光る」と読める。**
実際に読み違えた（2026-08-31）。さらに、ラベルは「直す前の症状」なのに、選ぶと効くのは
その**打ち消し**なので、3 色が回る 2 つ（BGR / RBG）は**正しいテープで試すと逆回りに見える。**
文で説明しきれる形ではない。

**3 案目（採用）：並びを当てさせない。見えた色を 2 つ答えてもらう。**

```
NeoPixel は 赤が [ ▼] 緑が [ ▼] に見える
```

メニューは `赤` / `緑` / `青` の 3 つだけ。**1 つでは足りない**（赤だけだと 6 通りが
3 組に分かれるだけ）。**2 つで一意に決まる。**

| 赤が…に見える | 緑が…に見える | テープの並び |
|---|---|---|
| 赤 | 緑 | GRB（既定。直すところが無い） |
| 青 | 緑 | GBR |
| 緑 | 赤 | RGB |
| 赤 | 青 | BRG |
| 緑 | 青 | BGR |
| 青 | 赤 | RBG |

**赤と緑が同じ色に見えることはない。** 残り 3 通り（同じ色を 2 つ選んだ場合）は
何もせず、コンソールに警告を出す。

**⚠ 答えるのは「このブロックを置く前」の見え方。** 困っている人はまずその状態で
見ているので、これでよい。同じ答えをもう一度実行しても結果は変わらない。

#### 送る値

**並べ替えは送信直前の 1 か所だけで行う。`_neoFlush()` の `params.push`。**

| 並び | 送る順 |
|---|---|
| GRB | R, G, B（今までと同じ） |
| GBR | B, G, R |
| RGB | G, R, B |
| BRG | R, B, G |
| BGR | G, B, R |
| RBG | B, R, G |

導き方はこう。`NeoPixelmin` は渡した `(r, g, b)` を線へ `g, r, b` の順で出す。
テープの並びが XYZ なら、テープは線の 1 バイト目を X として読む。GBR のテープなら
1 バイト目（= 渡した `g`）を G、2 バイト目（= 渡した `r`）を B、3 バイト目を R と
読むので、渡す値は `(B, G, R)` になる。

決めごと。

- **既定は GRB。** 今までの挙動を変えないので、保存済みの作品は無傷
- **接続前でも設定できる。** 「始める」の**上**に置くのが自然な位置なので、
  `_neoReady()` で弾かない。`neoBegin` でも既定へ戻さない
- **切り替えたら全画素を dirty にする。** 途中で変えても次の表示で反映される
- **デバイス側（`.ino`）は変更しない。** `PROTOCOL_VERSION` は 8 のまま、
  **焼き直し不要**

ライブラリ側で `NeoPixelmin(n, pin, NEO_BGR)` と指定する手もあるが、それだと
`NEO_BEGIN` の引数を増やすことになり、全員に焼き直しをお願いすることになる。
JS 側で済むならそちらが軽い。

### 引数の型と範囲

| 引数 | 型 | 範囲 | 範囲外のとき |
|---|---|---|---|
| `SEEN_R` / `SEEN_G` | `STRING`（メニュー） | `R` / `G` / `B` | 2 つが同じ色なら**何もしない**（コンソールに警告） |
| `COUNT`（始める） | `NUMBER` | 1〜64 | 丸める |
| `BRIGHTNESS` | `NUMBER` | 0〜100 % | 丸める |
| `INDEX` | `NUMBER` | 1〜個数 | **何もしない**（黙って落とす） |
| `COLOR` | `COLOR` | `#rrggbb` | — |
| `R` / `G` / `B` | `NUMBER` | 0〜255 | 丸める |
| `H` / `S` / `V` | `NUMBER` | 0〜100 | H は剰余、S / V は丸める |
| `STEP` | `NUMBER` | 整数（負も可） | 個数で剰余を取る |
| `PERCENT` | `NUMBER` | 0〜100 % | 丸める |
| `OFFSET` | `NUMBER` | 0〜100 | 剰余を取る |

**色相・鮮やかさ・明るさは 0〜100 に揃える。** Scratch のペン
（`ペンの色を [ ] にする` など）が 0〜100 なので、そちらに合わせる。
0〜255 や 0〜360 を混ぜると、同じ「色」という言葉で別の目盛りを使うことになる。

`INDEX` が範囲外のときに何もしないのは、Scratch のリストと同じ振る舞い。
`[0] 番`（1 から数えるので存在しない）や `[13] 番` を黙って捨てる。
**ただし開発者コンソールには警告を出す。** 無言で消えるのが一番分かりにくい。

## 3. ワイヤフォーマット

コマンド ID は **`0x60`〜`0x64`** の 5 つ。

`0x50` 台を避けたのは、Input Report のマーカー（`0x50`=コンソール / `0x52`=応答 /
`0x53`=READY / `0x54`=シリアル受信）と番号が紛らわしいため。
向きが違うので実際に衝突はしないが、`hid-console.html` で生バイトを追うときに
目で混ざる。

### `NEO_BEGIN` (`0x60`) — 使い始める

| バイト | 内容 |
|---|---|
| `[0]` | `0x60` |
| `[1]` | LED の個数（1〜64） |

デバイスはこの個数で `pixels` を作り直してから `begin()` を呼び、`neoOpen` を立てる。
以後 D8 は弾かれる。0 と 65 以上は `RSP_ERR`。

**バッファの入れ物は作り直しても変わらない**（`_buf` は常に 64 個分の固定配列）ので、
RAM は増えない。明るさは 0（無変換）に戻るが、Scratch 側は直後に
`NEO_BRIGHTNESS` を送るので表に出ない。

閉じるコマンドは無い。シリアルと同じ考え方で、
一度使い始めたピンはリセットするまで返さない。

### `NEO_SET` (`0x61`) — 連続する何個かの色を書く

| バイト | 内容 |
|---|---|
| `[0]` | `0x61` |
| `[1]` | 開始番号（**0 から数える**） |
| `[2]` | 個数（1〜9） |
| `[3..31]` | R,G,B × 個数 |

**1 コマンドで 9 個分。** Feature Report は 32 バイトで、
使えるのは `[3..31]` の 29 バイト。3 バイト × 9 = 27 バイトで収まる。

⚠ **ブロックの `[1] 番` は、ここでは `0` になる。** 変換するのは Scratch 側。
デバイスは 0 から数える（`NeoPixelmin` の `setPixelColor()` がそうなっている）。

`開始番号 + 個数 > 64` なら `RSP_ERR` を返す。

### `NEO_FILL` (`0x62`) — 範囲を 1 色で埋める

| バイト | 内容 |
|---|---|
| `[0]` | `0x62` |
| `[1]` | 開始番号（0 から数える） |
| `[2]` | 個数（**0 = 最後まで**） |
| `[3]` | R |
| `[4]` | G |
| `[5]` | B |

`NeoPixelmin::fill()` の引数の並びと同じ。個数 0 が「最後まで」なのもライブラリに合わせた。

**Scratch 側が使うのは「消す」（全部 0）のときだけ。**
それ以外の塗りつぶしは鏡のバッファを書いて `NEO_SET` で送る。
`NEO_FILL` を残してあるのは、停止時の消灯を 1 往復で済ませるため。

### `NEO_SHOW` (`0x63`) — 送り出す

| バイト | 内容 |
|---|---|
| `[0]` | `0x63` |

`pixels.show()` を呼ぶ。**これを送るまで LED は変わらない。**

`show()` の中で 300µs のリセット待ちが入る（`NEOPIXELMIN_RESET_US`）。
送出は LED 1 個あたり 32µs（24 ビット × 1.33µs）で、12 個なら合わせて約 0.7ms。
応答が返るのはその後なので、`SHOW` だけ他のコマンドより少し遅い。
既定のタイムアウト 3 秒には十分収まる。

**この間は割り込みが止まる**（次節の `NEOPIXELMIN_ATOMIC`）。

### `NEO_BRIGHTNESS` (`0x64`) — 明るさ

| バイト | 内容 |
|---|---|
| `[0]` | `0x64` |
| `[1]` | 0〜255 |

`pixels.setBrightness()` を呼ぶ。**このライブラリの明るさは非破壊的で**、
バッファの値は変えずに送り出すときだけ掛ける。したがって
明るさを変えた後も `SHOW` を送れば、色を入れ直さなくても反映される。

Scratch 側の `0〜100 %` からの変換は `Math.round(percent * 255 / 100)`。

⚠ **`setBrightness(0)` は消灯。** Adafruit と同じ意味づけで、
内部では `b + 1` を保持して `(v * (b+1)) >> 8` で掛けるため、
0 は「1/256 倍」ではなく完全に 0 になる。

## 4. デバイス側スケッチ

### 分岐は `CMD_MOUSE_MOVE` より **前** に置く

```c
  // NeoPixel はピン番号を取らないので、下のピン検査より前に分岐する。
  // ⚠ マウスの判定より前に置くこと。0x60 は 0x40 以上なので、
  //   後ろに置くと if (cmd >= CMD_MOUSE_MOVE) に吸い込まれる。
  if (cmd >= CMD_NEO_BEGIN && cmd <= CMD_NEO_BRIGHTNESS) {
    doNeoPixel(cmd, buf);
    return;
  }

  if (cmd >= CMD_MOUSE_MOVE) {
    doMouse(cmd, buf);
    return;
  }
```

**これが一番踏みやすい穴。** `0x60 >= 0x40` なので、順番を間違えると
NeoPixel のコマンドが全部マウスへ行く。`doMouse()` は既定で `rsp_err()` を返すので、
症状は「ブロックが無言で何もしない」になる。

### `#include` の前に `NEOPIXELMIN_MAX_LEDS` を定義する

```c
#define NEOPIXELMIN_MAX_LEDS 64
#include <NeoPixelmin.h>

static NeoPixelmin pixels(NEOPIXELMIN_MAX_LEDS);
static bool neoOpen = false;
```

定義せずに `#include` すると `#error` で止まる。ライブラリが意図的にそうしてある
（既定値を置くと、少なすぎて黙って切れるか多すぎて RAM を無駄にするか、
どちらも実機に載せるまで分からないため）。

64 個で RAM は 192 バイト。1m 60 個のテープまで入る。

### ⚠ `NEOPIXELMIN_ATOMIC` が要る。これが無いと実機で不規則に光る

```c
#define NEOPIXELMIN_ATOMIC
#include <NeoPixelmin.h>
```

**2026-08-12、実機で最初に踏んだ不具合がこれ。**
`始める` を押すたびに、消えているはずの 2 番が緑に点いたり点かなかったりした。

WS2812 は途中で 50µs 以上止まると、そこで 1 フレームが確定したと見なし、
次のバイトから別のフレームとして解釈し直す。UIAPduino の USB は
ソフトウェア実装（rv003usb）で、その割り込みは 50µs を超える。

ライブラリの既定は「割り込みを許す」で、波形を GPIO ではなく SPI1 で作るのは
そのためだが、それが成り立つのは **1 レジスタ書き込みあたり 2.67µs の余裕に
収まる割り込みだけ。** ソフトウェア USB はそこに収まらない。
ライブラリはこの逃げ道を最初から用意している（`NeoPixelmin.h` の Configuration）。

#### ⚠ ライブラリの例が動いたことを根拠にしない

`NeoPixelmin_ring` の例は実機で動いている。それでも足りなかったのは、
例といまのスケッチで条件が 2 つ違うため。

| | 例（動いた） | このスケッチ |
|---|---|---|
| バッファの LED 数 | 12（`show()` は 0.38ms） | 当初 64（**2.05ms**） |
| USB 設定 | `usb=webhid`（インタフェース 1 つ） | `usb=kbdweb`（**3 つ**） |

送出時間が 5.3 倍で、しかもホストがキーボードとマウスの分まで常時ポーリングする。
割り込みが送出中に入る確率がまるで違う。**「ライブラリは実機確認済み」は、
この使い方で動く根拠にならなかった。**

### D8 をピン操作から弾く

```c
static bool digitalPinOk(uint8_t pin) {
  if (pin >= NUM_DIGITAL_PINS) return false;
  if (serialOpen && (pin == PIN_UART_TX || pin == PIN_UART_RX)) return false;
  if (neoOpen && pin == PIN_NEOPIXEL) return false;
  return pin != PIN_USB_DP && pin != PIN_USB_DM && pin != PIN_RESET;
}
```

**`analogChannelOk()` は変更不要。** D8 = PC6 にはアナログチャンネルが無い
（A0〜A7 は PA2 / PA1 / PC4 / PD2 / PD3 / PD5 / PD6 / PD4）。
シリアルの D15 / D16 が A5 / A6 でもあったのとは事情が違う。

`PIN_NEOPIXEL` は `NEOPIXELMIN_PIN`（= `PIN_SPI_MOSI` = 8）と同じ値だが、
スケッチ側にも名前を置いて、他のピン定数と並べて読めるようにする。

### 停止時の消灯

Scratch 側の `PROJECT_STOP_ALL` から `NEO_FILL(0, 0, 黒)` + `NEO_SHOW` を送る。
**デバイス側の変更は要らない。** 既にあるコマンドで足りる。

`CMD_PANIC` に混ぜないこと。あちらはキーとマウスを離すためのもので、
NeoPixel が繋がっていない作品でも必ず飛ぶ。用途が違うものを 1 つのコマンドに
まとめると、どちらの都合でも変えられなくなる。

## 5. Scratch 側の作り

### 鏡のバッファ

```js
/** 明るさを掛ける前の RGB。3 バイト × 64。 */
this._neoBuf = new Uint8Array(NEOPIXEL_MAX_LEDS * 3);
/** 「始める」で渡された個数。送る範囲を決めるのはこの値。 */
this._neoCount = 0;
/** 「始める」を実行したか。していなければ光らせるブロックは何もしない。 */
this._neoOpen = false;
/** テープの色の並び。NEOPIXEL_ORDER のキー。既定は 'GRB'。 */
this._neoOrder = NEOPIXEL_ORDER_DEFAULT;
```

**論理的な RGB の順**で持つ。テープの並びに合わせるのは送信直前の
`_neoFlush()` だけなので、`n 番の色`・虹・HSV・`ずらす`・`暗くする` は
色の並びの設定に一切影響されない。

### 送るのは変わったところだけ

自動表示が既定 ON なので、`[1] 番を赤にする` を 1 個置いただけでも送信が走る。
毎回 64 個分（`SET` × 8 + `SHOW` = 9 往復 ≒ 135ms）送っていては、
ブロック 1 個が体感で引っかかる。

そこで**変わった範囲だけ**を覚えておき、その範囲の `SET` だけを送る。

```js
/** 前回の送信以降に書き換えられた範囲（両端を含む）。空なら from > to。 */
this._neoDirtyFrom = 0;
this._neoDirtyTo = -1;
```

1 個だけ変えたなら `SET` 1 回 + `SHOW` 1 回の 2 往復（≒ 25〜30ms）で済む。
虹のように全部を書き換えたときだけ 9 往復になる。

⚠ **`SHOW` は必ず送る。** 変わったところが無くても、明るさだけ変えた場合や
利用者が明示的に「表示する」を置いた場合があるため。

### 「まとめて表示する〔 〕」

マウスの `ドラッグしながら〔 〕` / キーボードの `[Ctrl] を押しながら〔 〕` と
同じ `BlockType.LOOP`。「中身が終わったらもう一度呼ばれる」性質を使う。

```
1 回目の呼び出し : 自動表示を止める → util.startBranch(1, true) → 中身が動く
2 回目の呼び出し : 自動表示を戻し、溜まった分を 1 回で送る
```

入れ子にできるよう**深さで数える**（`_neoBatchDepth`）。0 → 1 で止め、1 → 0 で送る。
修飾キーの `_modifierCounts` と同じ考え方だが、こちらは種類が 1 つしかないので
`Map` ではなく数値 1 つでよい。

⚠ **停止したときに深さを戻すこと。** 囲みの途中で止められると 2 回目の呼び出しが
来ないので、`_neoBatchDepth` が 1 のまま残る。次に緑の旗を押しても
自動表示が効かなくなり、「急に光らなくなった」に見える。
`_releaseInput()`（`PROJECT_STOP_ALL`）で 0 に戻す。

### 色の計算はすべて JS 側

| ブロック | 計算 |
|---|---|
| HSV | 色相 0〜100 → 0〜360 に直してから RGB へ |
| 虹 | 個数で 1 周。`色相 = (i / n + ずらし / 100) % 1` |
| ずらす | バッファを 3 バイト単位で回す。個数で剰余（`n` を超えるずらしも一周する） |
| 暗くする | 各成分に `(100 - percent) / 100` を掛けて丸める |

**`暗くする` は明るさ（`BRIGHTNESS`）とは別物。** あちらはデバイス側で
送り出すときに掛かる非破壊的な倍率で、バッファは変わらない。
`暗くする` はバッファそのものを書き換えるので、繰り返すと消えていく。
残像やフェードアウトを作るのはこちら。

### 「始める」を実行していないとき

`_neoOpen` が false のうちは、光らせるブロックは**何もせずに返す**。
シリアルの `_serialSend()` と同じ形で、開発者コンソールに警告を出す。

```js
console.warn('[uiapduino] NeoPixel is not started; place the "start NeoPixel" block first');
```

⚠ **Xcratch では、ページを読み込み直すたびに「始める」の実行が要る。**
拡張機能が作り直されるので `_neoOpen` が false に戻る。シリアルと同じ落とし穴。

### Flash 使用量（FQBN は `sketch.yaml` と同じ）

| | Flash | RAM |
|---|---|---|

リセット待ちひとつのために払うことになっていた。

### 確認済み（2026-08-13 / WS2812B 12 連リング）

| 確かめたこと | 結果 |
|---|---|
| 不規則な点灯が止まった（`ATOMIC` と個数指定の効果） | ✅ |
| 虹が回る。`ずらし` は 100 で一周（20 倍したタイマーで 5 秒／周、100 倍なら速い） | ✅ |
| **虹を回しながら `キーボードで [a] と打つ`。** 打ち漏らし・化け・接続切れなし | ✅ |
| **同上を `64 個` で。** 割り込みを 2.05ms 止めても USB は落ちない | ✅ |
| `まとめて表示する〔 〕` の中では光らず、抜けた瞬間にまとめて変わる | ✅ |
| 停止ボタンで消灯。囲みの途中で止めても、次の緑の旗でふつうに光る | ✅ |
| `明るさ` は非破壊（色を入れ直さず反映・戻せる）。`暗くする` は破壊的（戻らない） | ✅ |
| `始める` の後に D8 へデジタル出力しても弾かれ、LED は回り続ける | ✅ |
| 範囲外の番号（12 個のときの 13 番）は何も起きない | ✅ |

**64 個の試験はリング 12 個のままで足りる。** 光るのは 12 個でも、送出時間と
割り込みを止める時間は 64 個分かかるので、USB への負荷は同じになる。

### 確認済み（2026-08-31 / 色の並び / WS2812B 12 連リング）

まず、このリングの並びを判定した。`1 番 = 赤(255,0,0)` / `2 番 = 緑(0,255,0)` /
`3 番 = 青(0,0,255)` を出したら**そのまま赤・緑・青**が出たので **GRB**。
見えた組み合わせは 6 通りのうち GRB にしか当たらない。

そのうえで 6 通りの並べ替えを全部試し、**予告した見え方と全部一致した。**
GRB のテープなので「直る」ところは見られないが、並べ替えが効いていることは
これで確かめられる。

**⚠ この確認は、並びを直接選ばせていた頃のビルドで行った。** その後ブロックは
「見えた色を答える」形に変わったが、**`_neoFlush()` の並べ替えは 1 行も変えて
いない**ので、結果はそのまま通用する。下の表の「選んだもの」は、いまのブロックでは
右端の答え方に読み替えること。

| 並び | 1 番（赤） | 2 番（緑） | 3 番（青） |
|---|---|---|---|
| ふつう (GRB) | 赤 | 緑 | 青 |
| 赤と青が入れかわる (GBR) | 青 | 緑 | 赤 |
| 赤と緑が入れかわる (RGB) | 緑 | 赤 | 青 |
| 緑と青が入れかわる (BRG) | 赤 | 青 | 緑 |
| 赤→緑→青にずれる (BGR) | 青 | 赤 | 緑 |
| 赤→青→緑にずれる (RBG) | 緑 | 青 | 赤 |

**この「ラベルと逆に見える」現象こそ、症状メニューをやめた理由。**
詳しくは「⚠ 並びを選ばせてはいけない」を見ること。

**青だけ暗いのは正常。** WS2812B は素子の光度が青でいちばん低く、目の感度も
青で最も低い。故障でも並び違いでもない。むしろ**「暗い 1 個」が青を頼んだ LED に
付いてくること自体が、並びの裏取りになる。**

#### まだ見ていないもの

D7 / D9 / D3 が空いたままであること、`始める` を置かずに実行したときの警告、
`明るさ 0%` での消灯、64 個を実際に繋いだときの電流。

### 一覧（作り直したときの再確認用）

### 先に机上で確かめてあること

`processor.request` を差し替えると、デバイス無しでコマンド列を検証できる
（キーボードのときと同じやり方）。実装した時点で次の 34 項目が通っている。

- ブロックが 14 個そろい、`neoBatch` が LOOP、`neoGetColor` が REPORTER、色が色ピッカーになる
- 始める前は何も送らない / `始める` は BEGIN → BRIGHTNESS → FILL → SHOW の順
- 1 個だけ変えたら `SET` 1 回 + `SHOW` 1 回。12 番だけ変えたら開始番号 11 で 1 個ぶん
- 範囲外の番号（0 番 / 13 番）は何も送らない
- 虹は `SET` 2 回（9 個 + 3 個）+ `SHOW` 1 回。1 番が赤
- 囲みの中では送らず、抜けたときに 3 個まとめて 1 回で送る。入れ子も外側でだけ送る
- 停止で PANIC → FILL → SHOW が飛び、囲みの深さが 0 に戻って自動表示が復活する
- ずらす（正・負・個数ぶん・個数超え）、暗くする、HSV の各境目
- `10 番から 5 個` は 12 個のリングで 3 個だけ塗る
- 始めた後だけ D8 を弾き、D7 / D9 と A ピンは弾かない

**これで分かるのはコマンド列だけ。** 波形もタイミングも色の見え方も検証していない。
下記はすべて実機で見ること。

1. 基板を書き込み直してから接続し、バージョン照合が通る（デバイス = 8）
2. `始める` を実行せずに色のブロックを置くと、何も起きずコンソールに警告が出る
3. `[1] 番を [赤] にする` を 1 個置いただけで光る（自動表示）
4. `全部 [青] にする` → `消す` で消える
5. `明るさ [10] %` にすると暗くなり、**色を入れ直さなくても**次の `表示する` で反映される
6. `明るさ [0] %` で消える
7. `[13] 番`（個数 12 のとき）を指定しても何も起きず、警告が出る
8. `虹を出す` の `ずらし` を 0→100 と動かすと、色が一周して元に戻る
9. `ずらす` に負の値・個数を超える値を渡しても一周する
10. `暗くする` を繰り返すと消えていく。**`明るさ` を戻しても復活しない**（バッファが変わっているため）
11. `まとめて表示する〔 〕` で囲むと、囲みの中は光らず、抜けた瞬間に反映される
12. 囲みの中で停止ボタンを押した後、次に緑の旗を押すと**自動表示が戻っている**
13. 停止ボタンで消灯する
14. `始める` の後に `D8` を `デジタル出力` しようとしても何も起きず、警告が出る
15. **D7 (SCK) / D9 (MISO) / D3 (NSS) は今までどおり使える**
16. 64 個を指定しても動く（RAM が足りている）

**2 / 11 / 12 / 13 が要点。** 2 は Xcratch で必ず踏む落とし穴、
11 は設計方針そのものの検証、12 は囲みブロックの後始末、
13 は「止めたのに光ったまま」を防ぐもの。

## 8. 引き継ぎメモ

### 分岐の順番

- **`0x60` はマウス (`0x40`) より大きい。** `if (cmd >= CMD_MOUSE_MOVE)` より
  前に置かないと、NeoPixel のコマンドが全部マウスへ吸い込まれる。
  症状は「無言で何もしない」なので気づきにくい

### ライブラリについて

- **`sketch.yaml` があると、手元で直したライブラリは使われない。**
  arduino-cli も IDE も profile build に入り、インストール済みコアではなく
  index から取り直したコアでビルドする。手元の修正を実機で試すときは
  `sketch.yaml` を外して `--fqbn` で焼くこと
- **`NeoPixelmin` は SPI1 を占有する。** `SPI.h` / `SDmin` と同居できない
- **`setBrightness()` は非破壊的。** バッファは変わらない。
  `暗くする` ブロックと混同しないこと

### ビルドについて

- **`.ino` を変えたら arduino-cli でコンパイルして確認すること。**
  利用者に「確認してください」と言わない。手順はグローバルメモリの
  `arduino_cli_build.md` にある
- Electron 版のビルドは指示されたときだけ。`xcratch` の rollup ビルドは聞かずに走らせてよい

### 既存の制約

- eslint は既存コードの時点で通っていない。**新種の違反を増やさなければ十分**
- `.ino` を正規表現で検査するときは CRLF に注意する。`/\/\/.*$/` は
  `.` が `\r` に一致しないため `//` コメントを 1 つも落とせない。`[^\r\n]*` を使う

**Issue [#3](https://github.com/tarosay/scratch3-uiapduino/issues/3)。**

戻さないこと。**

**6 種類すべて出すのは、見た目から並びを言い当てるのが無理だから。**
当初この仕様書と Issue #3 には「『赤と青が入れかわる』という報告があった
（= GBR）」と書いていたが、**その報告は存在しない。**
[#2](https://github.com/tarosay/scratch3-uiapduino/pull/2) の本文・コメント・
差分のどこにも出てこない（2026-08-31 に確認）。こちらが書いた文だった。
[#2](https://github.com/tarosay/scratch3-uiapduino/pull/2) の作者のテープは、
提出された修正が R と G の入れ替えだけだったことから **RGB** と見られる。

| | 直す前 | 直した後 |
|---|---|---|
| 線へ出す順 | `[G, R, B]` 固定 | 選んだ並びに合わせる（既定は同じ） |
| 並べ替える場所 | なし | `_neoFlush()` の `params.push` **だけ** |
| `_neoBuf` の中身 | 論理 RGB | **変えない**（論理 RGB のまま） |
| デバイス側 | — | **無変更。`PROTOCOL_VERSION` 8 のまま、焼き直し不要** |

**`_neoWrite()` でやってはいけない。** 鏡のバッファの中身が入れかわり、
`n 番の色` が入れかわった色を返す。「鏡は RGB の順で持つ」という前提も崩れる。

先に [#2](https://github.com/tarosay/scratch3-uiapduino/pull/2) で
@shimodash さんから同じ狙いの提案をいただいた。狙いは同じで、
2 種類ではなく 6 種類に広げたうえで実装した。

### 2026-08-12 — 実機で不規則に光った。`ATOMIC` と個数指定を入れた

**症状:** `始める` を押すたびに、消えているはずの 2 番が緑に点いたり点かなかったりする。

**原因:** ソフトウェア USB の割り込みが `show()` の途中に入り、WS2812 のフレームが
壊れていた。詳細は「[⚠ `NEOPIXELMIN_ATOMIC` が要る](#-neopixelmin_atomic-が要るこれが無いと実機で不規則に光る)」。

| | 直す前 | 直した後 |
|---|---|---|
| `show()` 中の割り込み | 許す（ライブラリの既定） | **止める**（`NEOPIXELMIN_ATOMIC`） |
| 送る LED の数 | 常に 64（2.05ms） | **`NEO_BEGIN` で渡された数**（12 個なら 0.38ms） |
| `NEO_BEGIN` | パラメータなし | `[1]` = 個数 |
| Flash | 11948 (72%) | 12040 (73%) |

**この 2 つはセット。** 割り込みを止めるだけでは、64 個分の 2.05ms のあいだ
USB がホストに応えられない。個数を縮めるだけでは、割り込みが入る確率が下がるだけで
不具合は残る。

「個数をデバイスに教えない」という当初の決めごとは変えたが、**その狙い
（LED を増やしても焼き直さずに済む）は変わっていない。** デバイスは個数を
覚えるだけで、値を持っているのは Scratch 側のままなので、
`始める` の数字を変えるだけで済む。

### 2026-08-12 — 実装。実物に合わせて更新

打ち合わせで決めた内容を書き起こし、そのまま実装した。設計から変えた点は無い。
書き起こしのときに決めた細部（打ち合わせに無かったもの）は次のとおり。

| 項目 | 決めたこと | 理由 |
|---|---|---|
| 番号の数え方 | **1 から** | Scratch のリストと同じ。デバイス側は 0 から数えるので、変換はブロックの実装が持つ |
| HSV の目盛り | **0〜100** | Scratch のペンに合わせた。0〜255 や 0〜360 を混ぜない |
| ブロックの数 | **14 個** | メモには「12 個」とあったが、列挙は 14 項目だった。列挙を採った |
| 送る範囲 | **変わったところだけ** | 自動表示が既定 ON なので、毎回 64 個分送るとブロック 1 個が引っかかる |
| 範囲塗りが端を越えたら | **最後の 1 個まで塗って止める** | `10 番から 5 個` を 12 個のリングに置くのは自然な書き方で、弾くと数を数えさせることになる |
| パレットの位置 | **シリアルの後ろ、キーボードの前** | 基板に繋ぐもの（ピン・サーボ・距離計・シリアル・NeoPixel）を続けて置き、PC を操作するもの（キーボード・マウス）と分ける |

実装後に測った Flash は **11948 (72%)** で、設計時の見積もり 11984 より 36 バイト小さかった。
